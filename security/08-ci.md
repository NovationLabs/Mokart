# CI de sécurité

## Pourquoi une CI de sécurité

Toutes les corrections de ce dossier peuvent sauter au prochain commit fait à deux heures du matin. La CI est là pour ça. Elle relit chaque pull request et dit non avant que la faille arrive sur dev.

On a repris la logique qu'on utilise sur nos projets chez Ramify. Le contrôle tourne sur la pull request, pas après le merge. Un check qui tourne après le merge arrive trop tard, Railway a déjà déployé. Et la protection de branche exige que le check soit vert pour pouvoir merger.

## Ce qui est vérifié

Le workflow s'appelle Security CI. Il est dans .github/workflows/security-ci.yml, parce que GitHub ne lit les workflows que dans ce dossier. Toute la logique est dans des scripts de security/ci. On peut donc les lancer sur sa machine exactement comme la CI les lance.

Le premier job cherche les secrets avec gitleaks. Il lit tout l'historique git, pas seulement le dernier commit. Une clé supprimée dans un commit reste lisible dans les commits d'avant. Aujourd'hui, l'historique est propre. Si un jour il trouve quelque chose, la règle est simple. On révoque la clé chez le fournisseur d'abord, on nettoie le code ensuite.

Le deuxième job audite les dépendances. pip-audit vérifie l'API, le front de l'agent et le fichier uv.lock de l'agent. npm audit vérifie app et web. Ce job a déjà servi. Il a trouvé des failles connues dans Starlette, la brique sous FastAPI, et dans python-dotenv, anyio, urllib3, langsmith et langgraph-sdk. On a mis à jour ces paquets dans ce même commit. Côté npm, il n'y a aucune faille critique, mais soixante trois élevées. Elles viennent presque toutes de react-scripts, qui n'est plus maintenu. Le job bloque sur les critiques et affiche les élevées dans le résumé, sinon il serait rouge en permanence.

Le troisième job lance CodeQL. C'est l'analyse statique de GitHub, gratuite sur un dépôt public. Elle suit le chemin des données dans le code et repère les injections SQL, les XSS ou les redirections ouvertes. Les résultats arrivent dans l'onglet Security du dépôt.

Le quatrième job passe trivy sur les Dockerfile et les docker-compose. Il a relevé que tous les conteneurs tournaient en root. On a corrigé les trois images Python, qui tournent maintenant avec un utilisateur sans droits. Les images nginx restent en root pour écouter sur le port 80, ce qui est leur fonctionnement normal.

Le dernier job calcule le score de conformité. Il l'affiche dans le résumé de la pull request. Il échoue si un contrôle critique est rouge ou si le score passe sous 60.

## Le reste de la chaîne

Dependabot surveille maintenant les paquets Python, npm, les images Docker et les actions GitHub. Il ouvre une pull request par semaine vers dev quand une mise à jour sort. Les petites mises à jour sont regroupées pour ne pas nous noyer.

Toutes les actions GitHub sont épinglées par leur empreinte complète et pas par un tag. Un tag peut être déplacé par un attaquant qui pirate le dépôt de l'action. C'est arrivé en 2025 avec tj-actions. Une empreinte, elle, ne bouge pas. Les outils téléchargés par les scripts sont aussi vérifiés par leur empreinte SHA-256 avant d'être lancés.

Les workflows existants déclarent maintenant des permissions en lecture seule et ne gardent plus le jeton GitHub après le checkout.

## Lancer en local

Sur Linux, depuis la racine du dépôt, chaque script se lance seul, par exemple security/ci/secrets.sh. Il faut Python, Node, uv et curl. Sur Mac, le plus simple est de lancer le score, qui ne demande que Python.

## Ce qu'il nous reste à faire

Dans les réglages GitHub du dépôt, il faut protéger dev et production. Il faut exiger une pull request avant de merger et cocher les cinq checks de Security CI comme obligatoires. Sans ça, la CI prévient mais ne bloque rien.

Il faut aussi activer le secret scanning et la push protection dans l'onglet Security. C'est gratuit sur un dépôt public, et GitHub bloque alors un push qui contient un secret connu avant même qu'il arrive sur le serveur.

À moyen terme, il faudra quitter react-scripts pour Vite. C'est ce qui fera disparaître les soixante trois failles npm.
