# CD de sécurité

## Comment on déploie aujourd'hui

Railway suit nos branches. Un push sur dev reconstruit l'environnement dev, un push sur production reconstruit la production. C'est pratique, mais rien ne vérifie ce qui part en ligne. Et rien ne vérifie non plus ce qui tourne vraiment une fois en ligne.

C'est le deuxième point qui compte le plus. Le code peut être parfait et la production fausse quand même. Une variable oubliée, un service privé qui reçoit un domaine public par erreur, une vieille version qui ne s'est pas mise à jour. Chez Ramify, on sépare toujours les deux. La CI vérifie le code, la CD vérifie ce qui est déployé.

## Ce qu'on a mis en place

Le workflow s'appelle Security CD, dans .github/workflows/security-cd.yml. Les scripts sont dans security/cd. Il a deux parties.

La première est la porte avant déploiement. Elle tourne à chaque push sur dev ou production. Elle construit les images de production, les passe dans trivy et bloque s'il reste une faille critique qui a déjà un correctif. Elle lance ensuite la stack de production avec docker compose et rejoue toutes les attaques de l'audit contre elle. Si une seule passe, la porte est rouge.

Pour que cette porte bloque vraiment Railway, il faut activer l'option Wait for CI dans les réglages de chaque service Railway. Railway attend alors que les checks GitHub du commit soient verts avant de déployer. Sans cette option, Railway déploie en parallèle et la porte sert seulement d'alerte.

La deuxième partie vérifie l'environnement en ligne. Elle tourne après chaque déploiement réussi que Railway signale à GitHub, et tous les matins de toute façon. Elle appelle les vraies adresses, api.mokart.fr, app.mokart.fr, mokart.fr et ai.mokart.fr. Elle vérifie que l'admin répond 401 sans jeton et avec un faux jeton, que les sessions, le profil et le tableau de bord sont fermés, que Swagger est coupé, que le CORS refuse un site inconnu, que le compte démo est désactivé en production, que les en-têtes de sécurité et le HTTPS strict sont là, et que l'agent refuse les requêtes géantes.

Ce ne sont que des requêtes de lecture, sans compte, comme le ferait n'importe quel visiteur. Rien n'est créé ni modifié, et la vérification ne coûte rien sur la clé LLM.

Si un contrôle échoue, le workflow ouvre une issue GitHub avec le lien du rapport. Il n'en ouvre pas une nouvelle tant que la précédente est ouverte, pour éviter le spam.

On a testé le script sur une copie locale. Sur le code d'origine de dev, il trouve huit écarts sur neuf. Sur le code de cette branche, il passe douze contrôles sur douze.

## Les adresses

Les adresses par défaut viennent de docs/railway.md. Si elles changent, il suffit d'ajouter des variables de dépôt dans GitHub, par exemple PROD_API_URL ou DEV_APP_URL. Le workflow les prendra à la place.

## À quoi s'attendre après le merge

La vérification du matin regarde la production. Tant que ces corrections ne sont pas promues de dev vers production, elle va échouer et ouvrir une issue. C'est voulu. Ça nous rappelle que la production est encore vulnérable.

Pour la lancer à la main, il faut aller dans l'onglet Actions, choisir Security CD, puis Run workflow, et choisir l'environnement.
